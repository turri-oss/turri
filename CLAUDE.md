# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

turri is a harness that builds code from \*\*\*plain specs (`.plain` files). The harness, not the agent, decides what runs next and when work is done. It runs as a [pi](https://github.com/earendil-works/pi) extension (`turri`) and as a CLI for unattended runs. `docs/` describes the behaviour in detail. `docs/regenerating.md`, `docs/sandbox.md` and `docs/skills-and-gates.md` are the ones to read before changing the harness.

## Commands

```bash
npm install && npm link                        # `turri` on PATH, pointing at this clone (edits apply at once)
npm run typecheck                              # tsc --noEmit - covers src/ only, not tests/
npm run build                                  # src/ compiled into dist/ - the npm package only; npm pack runs it
npm test                                       # the whole vitest suite, about a minute
npx vitest run tests/regenerate/records.test.ts    # one file
npx vitest run tests/regenerate/loop.test.ts -t "one suite"   # matching tests in one file (-t alone still loads every file)
npm run chat                                   # pi with the extension loaded straight from src/
turri parse tests/data/simple.plain      # parse ***plain - its syntax and structure: no model, no API key
turri regenerate <file.plain> --dry-run      # look ahead: plan the work as regenerate would, print each codebase's next prompt, start nothing
turri init-config                        # a quick start config.turri.yaml in the current folder: the two models, every other setting at its default
turri doctor                             # what the machine lacks (bash, the OS sandbox, a model provider; in a project, its toolchains)
```

Tests that run real commands behind the OS sandbox are wrapped in `runIf(sandboxAvailable().kind !== "none")` and skipped silently on a machine without one; the rest run everywhere (the process-group ones skip on Windows). `tests/setup.ts` kills every process group a file left when it finishes. The testing scripts run on this machine, as in turri. The suite takes about a minute.

## TypeScript runs unbuilt

`bin/turri.mjs` checks for Node >= 22.19 and imports `src/cli.ts` directly. Node's own type stripping runs the sources and nothing compiles them - except for the npm package, where Node will not strip types inside `node_modules`: `npm run build` compiles `src/` into `dist/` file for file, and `bin/turri.mjs` runs `dist/cli.js` when there is no `src/`. So:

- imports use explicit `.ts` extensions;
- don't use syntax that type stripping can't erase: parameter properties (`constructor(readonly x: T)`), `enum`, `namespace`. Declare the field and assign it in the constructor. `tsc` and `tsx` (the `npm run regenerate`-style scripts) both accept these, so they only fail when run through `turri`.

## Linux, macOS and Windows

turri is developed for all three, as equals: no code assumes the OS it is written on. Where the OSes differ, the code asks Node (`node:path`, `node:os`, `process.platform`) rather than hard-coding one's answer, and what only one OS has - Seatbelt, bubblewrap, process groups - is behind a check for it, with what the others do instead said beside it. On Windows, bash is Git Bash.

- **A path on disk** is built and taken apart with `node:path` - `join`, `resolve`, `dirname`, `basename`, `relative`, `sep` - never with `/` in a template string, `+ "/"`, or `split("/")`.
- **Inside a folder** is `isWithin(path, root)` (`regenerate/paths.ts`), never `startsWith(`${root}/`)` or `relative(...).startsWith("..")`: a Windows path does not start with `root/`, and one on another drive gives `relative` an absolute path.
- **A name, not a place** - a file of a codebase, a .plain file in a diff, anything compared with git's paths or the parser's - is written with `/` on every OS: `slashed(relative(...))`, and `posix.join` to build one. `listFiles` gives codebase files so. Git pathspecs and refs, `stdlib/...` imports and `provider/model` ids are such names.
- **A path handed to bash** - a testing script's arguments, a `bash -c` script's - is `slashed`: Git Bash's tools may read a backslash as an escape (GNU tar took the `\a` of `C:\Users\anton` for a bell). Better still, give the tool no path at all: run it with `cwd`.
- **Lists of paths** split on `delimiter` (`;` on Windows), never `":"`; temporary folders come from `tmpdir()` and the person's home from `homedir()`, never `/tmp` or `process.env.HOME` (unset on Windows outside Git Bash).
- **The genome too.** What the skills and rules teach agents runs on the person's machine: a testing script is Bash for macOS's bash 3.2, Linux and Git Bash at once (the testing-script skills' *Bash specifics*), and their reference scripts in `assets/` are run on macOS and on Linux (Docker) after a change.
- **Tests** of what differs on Windows run everywhere: `tests/windows-paths.test.ts` mocks `node:path` with Node's `win32` and runs turri's own code on `C:\` paths. A fix for one OS comes with a test there, or one that fails on that OS's tools - checked against them (Docker for Linux's GNU tools) before the fix.

## Architecture

**Names.** `plain_modules` and `.plaingit` are the ***plain language's, not turri's, and keep their names.

**Entry points.** `src/cli.ts` dispatches `turri <cmd>`: `regenerate` (with `module:func-id`s: regenerated again; `--dry-run`, a look ahead - `WorkLoop.lookAhead`), `drift`, `conform`, `parse`, `lineage`, `launch`, `cultivate` and `capture` import `regenerate-cli.ts`, `drift-cli.ts`, `conform-cli.ts`, `parse-cli.ts`, `lineage-cli.ts`, `launch-cli.ts`, `cultivate-cli.ts` and `capture-cli.ts`, each of which parses `process.argv` itself; the ones that build share `loop-cli.ts` `runLoop`, which drives the work loop as the chat does. `doctor` goes to `setup.ts`, `init-config` to `init-config.ts`, and `install`, `update`, `remove` and `list` to pi's own `main` - its package commands, as users have no `pi` on the PATH (`update` refused where it would update pi itself). `turri` alone - or with options - spawns pi through `pi-launch.ts`, which builds `src/extension.ts` into pi in-process (`main(args, { extensionFactories })`) - the extension that registers every conversation tool and slash command (`regenerate`, `drift`, `conform`, `settings`, `pulses`, `halt`, `parse`, `cultivate`, `launch`, `/watch`, `/regenerate`, `/conform`, `/halt`, `/btw`, `/lineage`, `/settings`, ...). `/settings` (`settings.ts`, over `config-edit.ts`'s table of every key) writes config.turri.yaml line by line and applies what turri fixed at its start - the chat's model, the coding model given with `--coding-model`, `parallel-jobs` - live; it takes pi's own `/settings` over, pi's menu its last entry (`pi-settings.ts` patches `InteractiveMode`). The chat's `settings` tool reads and writes the same settings - into config.turri.yaml or a module's own file, a model resolved by the name the person said (`regenerate/model-names.ts`) - and refuses the keys marked `personOnly`, which `/settings` alone changes. A host that runs the chats itself - a desktop app - imports `@turri-dev/cli/host` (`src/host.ts`, compiled to `dist/host.js`, the package's only `exports` entry): `createTurri(options)` (`host-session.ts`) makes the session, opens, closes and focuses its chats, hands it the job registry and work loop and puts each chat's questions in its dialogs (`TurriHost`); the default export of `extension.ts` builds the extension into the process's one session (`processSession`, on `globalThis` so pi's own loader finds it too) (`docs/hosting.md`).

**Chats (`docs/chats.md`).** One turri process is one session (`createTurriCore` in extension.ts, over `chats.ts` `createChats`): one job registry and work loop, the ledger and the launch track, shared by up to nine chats. A chat is a pi session with the extension built into it, linked to its chat (`attach`); `scopedToChat` runs every tool, command and handler it registers inside the chat's scope (`chat-scope.ts`, an AsyncLocalStorage on `globalThis`), so `chosenStack`/`chooseStack` are the chat's, `jobs.start` tags `Job.chat` and the ledger tags `chat`. A pulse's end goes to the sentinel (`docs/sentinel.md`, `sentinel.ts`, `sentinel-chat.ts`; `sentinel: false` turns it off): a chat with `role: "sentinel"`, opened hidden by `jobFinished` with the first finished pulse and again after a close, in a slot of its own, told each pulse (`ChatInstance.brief`) in a fresh conversation - a new session under the same chat id (`freshConversation`, `host.onChatSession`), one pulse at a time, the rest waiting - while the chat the person looks at shows it (`landed`) - its agent told of one that landed only to say so and what the sentinel does with it (`landedNote`), and nothing more. The sentinel ends each pulse with `conclude` (`core.concluded`): the same chat shows it and its agent says it in a line (`concludedNote`). Its file tools and bash are `confinedTools` over the whole project, read only, and a `tool_call` guard refuses what is not in `SENTINEL_TOOLS`; what it finds it puts with `notify_person` as a notice (`core.notice`, one open a module) in the chat the person looks at - a card, a dialog once idle in the terminal, `onNotice`/`answer` for a host - and an answer starts that chat's agent on it (`act`). With it off, a pulse's end goes to its chat's `ChatInstance.announce`, or the shown chat's when it is closed. `session_start` fires each time a chat is shown, so a handler that must run once per chat guards itself. A driver says where chats live: `chat-terminal.ts` patches pi's `InteractiveMode`/`AgentSessionRuntime` to swap the runtime's live session instead of disposing it (`/new`, `/resume` open chats; a hidden chat draws on `chat-ui.ts`'s stand-in, its dialogs queued), `chat-commands.ts` has `/chat`, `alt+n`/`alt+w`/`alt+1…9` and the strip; `host-session.ts` makes a session per chat for a host. `chat-records.ts` keeps `.turri/chats.json` for `turri --continue` (pi-launch.ts turns it into `--session <first>` plus `restore`): closed chats and runs past the last five deleted, nothing in debug mode. pi's print/json/rpc modes have one chat, no driver.

**The \*\*\*plain parser (`src/plain/`)** is a faithful port of the Python reference parser (`plain_file.py`, `plain_spec.py`, `concept_utils.py`). Marshalled trees are compared against the Python output over a corpus, so behaviour, orderings and even list-indentation quirks are deliberate. See `docs/parser.md` before "fixing" one. It resolves linked resources against its template folders, the spec's own first; the tests name those folders by repo-relative paths, which is why vitest runs with `root: "."`. A functional spec is a `# <func-id>` heading and its text; a "func-id" (`add-task`) is unique in its module, and people and turri name a functional spec `<module>:<func-id>`. Its conformance and acceptance scenarios are in its test plain file, `<test-dir>/<module>/<func-id>.plain` (`test-plain-file.ts`), bound to it by its `module:` and `func_id:` and parsed with the module (`project.ts`; `ParseOptions.testDir`): a functional spec without one has no scenarios and is not tested. A section with no scenarios is a syntax error, and so is a file with no section - an empty test plain file is never written. `src/test-plain-files.ts` finds a module's test plain files and the strays, and refuses a test plain file where a module is asked for; `check.ts` is `parse`'s one check of a module with its test plain files. `GLOSSARY.md` names func-id, scenario-id and test plain file. `highlight.ts` reads turri's own TextMate grammar, `plain.tmLanguage.json`, which started from plyn's and no longer follows it.

**The standard library (`stdlib/`)** holds import modules that settle a generic piece of software on one stack - `stdlib/backend/python-flask`, `stdlib/cli/go-cobra`, ... Each stack imports its language's `stdlib/lang/<language>` and its kind's `common.plain`; its test reqs are a template of their own, `stdlib/<kind>/conformance/<stack>`, so a spec that skips conformance tests leaves it out. `stdlib/` is a reserved import prefix: `src/plain/stdlib.ts` reads such an import from turri's folder only, and a project module at the same path is an error. The templates define no concepts, and a `::` in them would be read as one. `src/stdlib.ts` appends the catalogue - every template, what it is, and the folder - to the `stdlib` rule when the rules load, so the rule never drifts from the files.

**Gated skills** (spec authoring): `genome/skills/*/SKILL.md` is parsed by `src/skill.ts` into steps (the `###` headings under `## Steps`) and gates (`metadata.gates` in the frontmatter). `src/graph.ts` compiles those into a LangGraph `StateGraph` (step -> gate -> route), and `src/judge.ts` runs independent judge sessions with a quorum. `src/genome.ts` `runSkill()` is the single entry point that both the CLI and the `cultivate` tool use. `src/rules.ts` appends every file in `genome/rules/` (the authoring rules, ~40k tokens, byte-identical so it stays cached) to spec-writing agents, never to coding agents. turri's own skills are found relative to the package, not the cwd. A skill that fails to parse is reported as pending, not dropped. `metadata.background: true` runs a skill in the background in the chat - `cultivate` returns at once, nothing shows, nobody is asked, and its end comes back to the chat once idle (`src/background-skills.ts`) - and `metadata.model: coding` runs it on the coding model of the module `cultivate`'s `plainFile` names; the two testing-script skills set both, and while one runs the work loop holds the modules that lack that script (`regenerate/scripts-being-written.ts`). A project's own skills, in `.turri/skills/` and `.agents/skills/`, are found beside them (`src/skills.ts`), turri's own winning a name; `.turri/.gitignore` lets `skills/` through.

**Regenerating the code (`src/regenerate/`)**, one unit of work at a time:

- A job is a spec diff: `regenerate.ts` `renderSpecDiff` regenerates one in the code, landing on its unit tests. `prompt.ts` builds the only thing the agent sees; it can't read `.plain` files, and it is told what to do with each functional spec by the job's cases (`cases.ts`: fresh, add, patch, again, delete, mechanical; again is the functional specs `regenerate` names, marked `regenerate_again` in the code record). The agent works, then the harness runs the project's unit testing script itself and inventories test files to catch deleted tests, sending the agent back up to 20 times - and for a best-guess draft when a turn wrote nothing. Once they pass, `unit-review.ts` has a read-only reviewer - one session for the loop, shown the whole work diff first, then the diff since its last review (`workSnapshot`) and the coder's `submit_work` account (`submit-work.ts`) - check that the code does what the spec says and its unit tests test it - an optimiser, not a gate: two reviews at most, the second weighed by an arbiter agent that passes on only what it upholds; after that fix the work goes on once its tests pass - as spec changes and conformance tests do too.
- `conformance.ts` writes black-box conformance tests into `plain_modules/<m>/tests` - exactly a functional spec's conformance and acceptance scenarios, at least one test each, labelled by scenario-id and checked by label; `conform.ts` runs it for a conformance job, then `regression.ts` runs the whole suite (a repair agent that may not touch tests).
- Nothing is queued (`docs/regenerating.md`). `loop.ts` works out what is left to regenerate - `drift.ts` `codeWork`, from the code record (`records.ts`: the spec of the codebase's whole requires chain, no test reqs, test plain files or scenarios) to the spec now - has `chunk-plan.ts` cut it into jobs from the functional specs outward (an agent groups them, by default, up to `max-specs-per-pulse`, code gives each group the definitions it uses, an agent places the reqs), and runs the first; again whenever a job ends or the spec changes. A chain is built in its tip codebase; the ones below are left behind. A running job the spec no longer wants is stopped (`stillWanted`) - unless the change is inside what it regenerates, which steers it instead (`steering.ts`: its agent told mid-turn or at its next turn, its record moved, twice a job at most). `regenerate` and `turri regenerate` both go through `bringUp`. Conformance is a second track in the loop: from `tests/.turri.json` to `conformanceTarget` (the functional specs with scenarios as built, their scenarios with them, and the test reqs), a conformance job - a spec diff's conformance run, the whole suite with it - once the module's code is built, before anything is built on it; `conform` runs it now. `conformance-tests:` turns it on, off when unset (`src/conformance-switch.ts`) - off by default for fast iteration, as conformance makes each change take about twice as long, and turned on by the person alone: off, no conformance pulse, no conformance testing script and the chat's `conform` refused - the chat told every turn what they are, that they are off and how they are turned on, and to tell the person why when it wants them; `/conform` (or a host's `turnOnConformanceTests`) turns them on, writing the key. On, the chat writes scenarios itself for a functional spec it judges needs them, by the criteria in `genome/rules/test-plain-files.md`, as a \*\*\*plain change like any other.
- `spec-steps.ts`: a tree written out one item a line, diffed with git into changes by id, and a step (`makeStep`) made of some of them - its tree, its diff, its text diff laid out as the module's file, a module below's functional specs as that module's.
- `records.ts`: `code/.turri.json` holds only the spec the code was built from, and `tests/.turri.json` what the conformance tests are written for. What is left is derived from them, never stored. Both pair functional specs by (module, func-id): a new func-id is an add, one gone a delete, changed text or scenarios a patch, one moved with its text unchanged nothing. A record written when functional specs were numbered (`isOldRecord`) is never built on: its chain is regenerated from scratch, with the person's go.
- `lineage.ts`: each `plain_modules/<m>` is a git repo with its git dir at `.plaingit`. Every unit of work starts from the last commit (`startWork`) and either commits or is rolled back whole (`abandonWork`), commits included. Code, tests and tree must never disagree.
- `notes.ts`: `code/.turri-notes.md`, the coding agents' working notes, and `tests/.turri-notes.md`, the conformance agent's - never one in the other. Agents edit them only through the `update_notes` tool, and every line is stamped by the harness.
- `test-scripts.ts` finds and runs the project's `run_unittests_*.sh` / `run_conformance_tests_*.sh`, from `config.turri.yaml` (with the module's own file over it), then the project root, then `test_scripts/` - never, for a module with no file of its own, a script another module's file names; such a module with no script waits for one of its own (`lacksOwnScript` in `loop.ts`). A script run is the only thing that decides pass or fail.

**Sandbox.** `confine.ts` rebuilds pi's file tools with a path check (argument and resolved path, symlinks resolved) that fences each agent to its own module's folders - `code/`, and `tests/` for the conformance roles - and gives it a `bash` on this machine behind `agent-shell.ts`: `command-check.ts` before each command, the module's environment (`agent-env.ts`), the OS sandbox (`os-sandbox.ts`: Seatbelt, bubblewrap) where one is up, `audit.ts` after, all run through the host runner `shell.ts` (a process group per command; `withPulse` kills what a pulse left running; a watcher and a start-up sweep for a turri killed outright). The testing scripts run on this machine unfenced (`testing-scripts-run-on: copy | in-place`), as does what a launch starts. turri turns off `AGENTS.md`/`CLAUDE.md` loading and pi's skills for every agent it starts (`noContextFiles`, `noSkills` in `src/pi.ts`).

**Agent sessions.** An agent's whole initial prompt is its system prompt (`createExecutor`'s `task`, opened with `BEGIN`), so pi's compaction never sums it up. The coding agent, the conformance agent, the code fixer, the repair agent and both reviewers keep one session per job and are compacted by the harness between turns past `compact-at` (`compactIfDue` in `pi.ts`, instructions per role in `regenerate/compaction.ts`); the arbiter, judges, explorer and planners stay fresh. Each job tallies its agents (`reportAgent`, `Job.agents`) into its log. Their sessions are in memory unless the project is in debug mode (`debug:`, `TURRI_DEBUG`, `--debug`: `debugMode` in config.ts) or the caller saves one (`saveSession` - a skill's run, which resumes from it). What a pulse writes only for a person - its log, its agents' debug logs, `read_output`'s and `service_logs`' outputs, its module's `tmp/`, the installed dependencies of the modules below it in its chain - is removed as it ends outside debug mode (`regenerate/pulse-files.ts`: `pulseWrote`, `pulseEnded`) - but why one that failed or finished without landing did is kept whatever the setting, `.turri/pulses/<id>.md` (`regenerate/failure-reports.ts`), and `pulses` tells it with an earlier session's pulse; the package caches are held to `cache-keep:` (`tidyCaches` in agent-env.ts).

**Launch (`regenerate/launch.ts`, `launch-track.ts`, `launch-session.ts`, `launch-agent.ts`, `launch-tools.ts`, `launch-cli.ts`; `docs/launch.md`).** Trying what is regenerated. Every launch goes through the session's launch track (`createLaunchTrack`): a codebase's launches one at a time, the newest commit waiting winning, none ever stopped for a newer one, nothing - no pulse, no chat - waiting on it; a commit whose code is out already does nothing. The harness exports the commit (`exportModule`, `git archive` of `<commit>:code` from `.plaingit` - the working tree never read or reset, the next pulse may be writing there) to `<project>/dist/<module>`, stops what the last launch started, and runs the launch agent (`runLaunchAgent`, on the codebase's coding model, thinking low): it finds the project's launch guidance (what the person said, AGENTS.md, a skill) and follows it from the host codebase, or starts the code from dist, installing what it needs in its own shell - nothing is put to the person - and ends with `submit_launch`, checked by the harness: a launch that says it serves is launched only while something it started with `activate` runs. What launches start is recorded in `.turri/launch/running/`; what a dead turri left there is stopped as a session starts and before each launch (`stopLeftBehind`). `activate`, the agent's alone, owns what keeps running, stopped on the next launch, `/halt launched <name | module>` and exit. Across a project: a launch replaces what launches of the modules below it in its `requires` chain started (waiting for one under way), and takes what turri's own launches of any other module hold that it needs - a port in `activate`, anything else through the agent's `stop_launched` - their launch `replacedBy` it, and what it stopped kept on it as `Launch.stopped`, apart from the agent's `summary` (`launchText` puts the two together for the chat, the terminal and the sentinel); `whoHolds` (launch.ts) says whose a process is from `.turri/launch/running/`, and a process no record names, or another live turri's, is never stopped. `track.runs` follows a module's code up the chain, so the sentinel tests a lower module's pulse in the launch above. The chat has one tool, `launch`, which returns at once and is told how it went once it ends. Under `launch-after-pulse: true` the work loop's `landed` callback - after the notes commit amends the pulse's commit - asks for a launch of the commit the pulse landed (`launch-session.ts`). The sentinel launches nothing: it checks every pulse in order, briefed only once its codebase's launches are settled and what runs holds the pulse's commit (`readyFor`; otherwise refused as turri's own error), paused while its codebase is launched again and resumed in the same conversation (`chats.ts` `pauseFor`).

**Capture (`src/capture/`, `capture-cli.ts`; `docs/capture.md`).** The person starts `turri capture [path]` or `/capture` to turn an existing codebase into ***plain in `<codebase>/plain`. `plan.ts` chooses compact or staged from `map.ts`'s file, line, byte and interface counts without a model. The plan and every answer are checkpointed in `.turri/capture/state.json`; checkpoints from before plans continue staged. `capture-analysis` uses the coding model with low thinking for the interface reference, splitting, outlining and dividing features. The `capture` role writes or corrects ***plain, including conventions and scenario trials. Agents are fresh, have a `submit_capture_*` tool each and their answers are checked (`checks.ts`, two retries); their prompts are in `genome/capture/`.

- **Shared start.** The survey settles each part's stack, concepts, conventions and test reqs. The conventions are checked against the code. The interface is extracted as data (`extractInterface`): the harness checks citations, literals and coverage against the map, then a fresh agent checks what literals cannot show. `resources/interface/<part>.md` is linked through the part's interface concept; writers get the reference and the stack's templates.
- **Writing.** Compact gives a small single-part program one writer and accepts a complete, validated module or expands to staged using the saved survey and reference. Staged splits areas above `LEAF_LINES`, outlines features and divides their ownership (`state.divided`), writes features side by side with scenarios budgeted by test evidence, then fills interface gaps. It gathers features into modules by concern and build order (`state.gathered`), reconciles conflicting definitions and runs a readability pass. Splitting is for the agents; modules are for the reader.
- **Shared finish.** Each module's interface is verified against the code (`state.corrections`); scenarios run on a copy of the original in `.turri/capture/trial/`, with a coding agent's shell, yielding corrections and test reqs (`state.trials`). `assemble.ts` writes modules, import modules, test plain files, assets and config. `capture/config.ts` carries the originating project's settings except its project-specific paths and turns conformance tests on. `scripts.ts` runs the two testing-script skills per part. `report.ts` records the parser check, gaps, decisions and failures. `progress.ts` reports the selected pipeline's phases, agents, activity and cost. A terminal chat can reopen in the captured project (`reopen.ts`); a desktop host opens its own projects.

**Jobs and progress.** In the TUI, the tools that regenerate start background jobs (`loop.ts`, `jobs.ts`). `lanes.ts` gives each job its spec's whole `requires` chain as lanes, so jobs whose chains overlap wait for each other and the rest run side by side - up to `parallel-jobs` at once (the registry's `maxRunning`). In pi's print/json/rpc modes the tools wait instead (`shouldWait`). Progress, usage and transcripts flow through an `AsyncLocalStorage` sink in `activity.ts` (`withActivity`, `reportStage`, ...) to `job-panel.ts` and the side panel (`jobs-tree.ts`), and to each pulse's log (`job-log.ts`).

**The ledger (`regenerate/ledger.ts`).** What turri does, as typed facts (`LedgerEvent`), through one `record()`, a JSON line each in `.turri/ledger/<time>-<run>-p<pid>.jsonl`: pulses from queued to finished, the work loop's halts, model calls and provider trouble (`ModelEvent` is bridged in), tool calls, script runs, gate rounds and verdicts, what turri refused, the healers (`healing()` wraps the debugger and the diagnosis, recording a failure instead of swallowing it) and the history's commits. Facts and pointers - and each pulse's ***plain diff (`job.diff`), so an earlier session's can be shown - never prompts or tool contents. A job's events find their project, pulse and module from the activity context (`currentPlace`); code outside a job passes a `LedgerPlace`. Observation, never control: nothing reads it to decide what to build - the records do. `ledger-view.ts` reads it back for the chat's `pulses` (the last runs of earlier sessions, and one pulse, this session's or an earlier one's); a host hears it live (`onLedgerEvent`) and reads it back through `src/host.ts`. Started by `extension.ts` and `loop-cli.ts` unless `TURRI_LEDGER=off`, which `tests/setup.ts` sets; the ledger's tests start it themselves.

**Projects.** A spec is built in its project: the nearest folder upwards holding `config.turri.yaml`, a `config.turri.<module>.yaml`, the old `config.yaml` or `plain_modules/` (`projectDirOf` in `paths.ts`). `config.turri.yaml` (`src/config.ts`) holds `module`, `harness-model`, `coding-model`, `judge-model`, `test-dir`, `base-folder`, `testing-scripts-run-on` and the script paths. `base-folder` names what a codebase requiring no module starts from instead of nothing - copied in once before its first pulse, recorded in `code/.turri-base.json`, carried up the chain with the code, its files listed to every coding agent (`regenerate/base-folder.ts`). A project whose parts are on different stacks - a backend and a frontend, each with its own testing scripts - gives a module its own settings in `config.turri.<module>.yaml`, laid over `config.turri.yaml` key by key. Nobody chooses it: the module's config (`configModuleFor` in `config.ts`) is its own file, else the one of a module it requires, all the way down its `requires` chain (`requiredModulesOf`, from the frontmatter alone); two among those it requires is an error - `check.ts` reports it as `parse` does, and `whenBuildable` in `loop-tools.ts` refuses the call, as it refuses a module that would be built with `config.turri.yaml` alone naming no unit testing script. The loop works it out each time it tracks a codebase and plans and starts its pulses under it (`ModuleState.configModule`, `withModuleConfig` in `loop.ts`), and a job keeps the one it was queued with (`jobs.ts`) - pinned in an AsyncLocalStorage (`withConfigModule`, `pinnedConfigModule`, `configModuleOf`), so code that knows only the project folder reads the pulse's; `configForSpec` reads the project's with the module's file over it. A config file that does not parse is read as empty - so it is said, never silently: under the chat's banner, by `turri doctor`, and in the refusal of every pulse and capture started on it (`configProblems`, `brokenConfig` in `config.ts`; `unbuildableConfig` in `loop-tools.ts`). turri never writes a `config.yaml` - it may be another tool's: a folder with no `config.turri*.yaml` is still read from `config.yaml` (and `config.<name>.yaml` as the module `<name>`'s) until turri first writes a setting, which copies them to the new names first (`adoptLegacyConfig`). `docs/config.md` documents every key.

## Testing patterns

- No test calls a model. Agent behaviour is scripted with `vi.mock("../../src/pi.ts", ...)` replacing `createExecutor` / `ask` with a stub that calls the session's tools directly (`write`, `run_unit_tests`, `update_notes`, ...). An agent's task comes as `opts.task` to `createExecutor` and its first `ask` is `BEGIN`: a stub that checks prompts reads the task from the session it made. The module under test is then loaded with a dynamic `await import(...)` after the mock. `tests/regenerate/conformance-loop.test.ts` is the reference example.
- `tests/test-scripts.ts` `writeTestScripts()` gives a temp project minimal Python testing scripts.
- The gate machinery (retry, escalation, no-artifact rejection) has no automated coverage. It is checked by live runs, see "Trying the gate semantics" in `docs/skills-and-gates.md`.

## Tools

A tool's name, description, guidelines and parameters sit in its agent's prompt every turn - the chat's alone are about 6k tokens - so tool text is written and pruned as prompt. The rules follow [Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents).

- **One tool per question the agent asks.** Shape a tool around the agent's question, not turri's internals: `pulses` answers everything about a pulse - live state, why it did not land, what the ledger recorded, this session's or an earlier one's. A new need extends the tool whose question it is; two tools that answer the same question are folded into one.
- **Modes are parameters, each obvious.** A parameter may switch what a tool returns when its description says which parameters go with which mode and what each defaults to.
- **The chat's tools serve the person's work.** A question only someone developing turri asks - counting ledger events - stays out of the chat.
- **Descriptions say what comes back, when to call it, and the sibling for the neighbouring question** (`drift`: "To see how it is planned into pulses, and the next pulse's prompt, use pulses with plain_file"), in turri's words of now - pulse, regenerate, \*\*\*plain diff. A renamed or removed concept is renamed or removed in every tool text too.
- **A failure is told so the agent can fix it.** A result that failed carries what failed and what shows it - the error, the end of the failing output, the next step - enough for the agent to debug it and tell the person. Long output is cut with an id `read_output` reads whole.
- **Structured results come through a `submit_*` tool**, called once; the harness reads its arguments, never the agent's prose. A new one gets a name of its own across turri, so the ledger and transcripts tell roles apart.
- **A tool lives while something uses it.** When the last role, skill or prompt that needs one goes, the tool goes, with what only it used - parameters, skill metadata, docs, tests. Before removing or renaming one, grep for its name in `src/` prompts, `SENTINEL_TOOLS`, `genome/`, `docs/` and `tests/`: a prompt naming a missing tool sends the model looking for it.
- **Wiring:** a tool reaches an agent only when it is in both `customTools` and that role's `tools: [...]` list; the chat's are registered in `extension.ts`.
- **Which tool the chat picks is learnt by running it.** No test calls a model, so check a change to the chat's tools against a few real prompts in the chat.

## Conventions

- The name is always **turri**, lowercase, even at the start of a sentence. \*\*\*plain is written `***plain` (escaped in Markdown).
- Prose in docs, comments and user-facing strings uses British spelling (behaviour, organised) and a spaced hyphen ` - ` rather than an em dash. Test names are sentences about behaviour (`it("renames a clashing file instead of overwriting it")`).
- When behaviour changes, update the `docs/` page that describes it in the same change.
- `genome/rules/turri-regeneration.md` is turri's model of itself for every agent that writes specs: what a spec change regenerates and where, what a coding agent sees, how bad code is fixed. When any of that changes, update the rule in the same change too - a stale one is worse than none, the agents reasoning from it with confidence.
- Commit messages follow [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/): `<type>[optional scope]: <description>`, then an optional body and optional footers, each after a blank line.
  - **type:** `feat` for a new feature, `fix` for a bug fix; otherwise `docs`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `style` or `revert`.
  - **scope:** optional, the part of turri it touches, in parentheses - `feat(stacks):`, `fix(regen):`, `docs(config):`.
  - **description:** lowercase, says what the system now does rather than what was edited, and carries no full stop.
  - **body:** the why and the details, when the subject alone does not say enough.
  - **breaking changes:** a `!` before the colon (`feat(config)!: ...`), or a `BREAKING CHANGE: <what changed>` footer - for example, a behaviour existing projects relied on that is gone.
  - Commits before this convention (see `git log`) are one long lowercase sentence; new ones are not.

## turri-app

turri-app, the desktop host (`../turri-app`), is read-only from here: read and grep it to see what a change reaches, and write nothing there - no file, no command that changes it. Whenever a change in turri must be reflected in turri-app, use the `turri-app-prompt` skill and ask the person to paste the prompt it writes into an agent session in turri-app.
