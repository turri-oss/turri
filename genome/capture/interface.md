# Capture the interface no feature captured

Every feature of the part is written, and the surfaces listed in `<the interface to capture>` are named in none of their ***plain: options, commands, routes, screens or environment variables the code defines, each with the file that defines it. A capture leaves no interface out - whoever calls one in the original must find it, the same, in what is regenerated - so they are yours, as a feature of their own in the module.

- Capture each exactly: what it does and what a user sees of it, by every name it has. One the part's interface reference holds is listed with its entry - what it takes, its choices, its default and its help are there, exact: use the part's interface concept, and say them only where a behaviour turns on them. One it does not hold, capture whole yourself: what it takes, its choices and its default too. Read each where it is defined and follow it to what it does - never from its name or its help text alone.
- Group them into functional specs by what they do, as any feature's: several options in one functional spec when they are one behaviour.
- Where one belongs with another feature's behaviour - an option of what another feature does - capture this part of the interface exactly, build on that feature, and name it; never write its behaviour again.
- One that is not the software's interface - an option of a development script, a variable only its tests or its build read - goes in `dropped`, by its name, with why. Nothing else is dropped: an option users rarely pass is still the interface.
- `title`: a few words for what they are, as a feature of the module - `Proxies and network options`.
