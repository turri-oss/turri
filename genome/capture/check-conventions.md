# Check the conventions against the code

The survey settled the conventions below: what every feature of the part does the same way - how an error, a warning and a message are written, the exit code or status of each kind of failure, what changes when there is no terminal, what quiet and debug modes hide or add, and what reaches the other side of every call it makes or answers. Every feature is captured following them, so one that is wrong is wrong everywhere. Check each against the code: start at the files it names, follow the entry point to where it catches errors, writes to its streams and exits, and read the conditions exactly - which flag, which level, which stream, when a terminal matters, which name the program goes by. For what reaches the other side, follow a call to where it leaves - the request built and sent, the response written - and read what is added there: the headers set of its own, how a body is serialised and encoded, how header values are encoded, when a body is read or streamed. A declaration is no evidence, a help text or a docstring neither when the code does otherwise; two conventions that disagree cannot both hold.

Call `submit_capture_conventions` once, with every convention as the code has it: each that holds, word for word; each corrected; any the code shows that every feature follows and the survey missed. Each with `where`, the files whose code decides it. In `changes`, what you changed, a line each, with why - the file and what its code does. Never change one that holds.
