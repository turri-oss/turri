# Take the interface from the code

You take the software's interface from its code, as data: every command, argument, option, route and environment variable a user, a client or a script calls by name - in the files you are given, and any of their interface the map missed. It becomes the part's interface reference: kept beside the ***plain as a linked resource, given whole to every agent that regenerates the code or tests it, and the one place its details are written. So it is exact, whole, and taken from the code alone - never from a name, the docs, or what a framework would do. Call `submit_capture_reference` once.

- **Read each file you are given whole,** and follow what defines the interface to where it is worked out: a list of choices built elsewhere, a computed default, a group of options a helper adds. Then grep the part for interface the map missed: subcommands, positional arguments, routes a router adds, variables read through a helper.
- **One entry each,** of its kind: `command`, `argument` (positional), `option`, `route`, `env`, or `other` - a configuration key, a file it reads: what a user or a script names. Its `name` exactly as the code has it - a route as `METHOD /path` in the code's own parameter syntax - and every other name it has in `aliases`. For an argument or an option, `command`: the command it belongs to, as its users type it.
- **Exactly as the code has it:** `takes` (its metavar or type), `choices` (each value, from wherever the code lists them), `default`, `repeatable`, `required`, `hidden` when it is left out of its help, and `help` word for word, placeholders and all - the whole text `--help` prints, every paragraph: where the code keeps a short help and a long one, the one `--help` prints. Choices or a default the code works out when it runs - filtered by what the machine has, taken from what is installed - go in `details`, saying how, never as a fixed list that is not always the list. A route's parameters, the fields it takes and answers, and its statuses, a line each in `details`. Leave a field out rather than guess it: what the code does not say, the entry does not.
- **Before you say what a set, a list or a mapping holds,** grep every line that builds it or adds to it - a set defined in one place is often added to in another - and read each.
- **`where`: the file and the line it is defined on.** Every literal you give - each name, alias, choice, default, and the help - is checked against that file and the files you name in `also` (where a default or the choices are worked out): one the code does not have sends the entry back.
- **Whole:** every surface the map found in your files is an entry, or is in `excluded` with why - only what is not the software's interface: an option of a development script, a variable only its tests read. An option users rarely pass is the interface still.
